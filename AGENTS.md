These documents must be read explicitly; GitHub does not automatically inherit them here.

The repository is an npm workspace with one lockfile and one version for all packages: `packages/core` (`@lunchbox-labs/model-profiles-core`, private and never published, all plugin logic), `packages/opencode` (`@lunchbox-labs/opencode-model-profiles`) and `packages/kilo` (`@lunchbox-labs/kilo-model-profiles`, for Kilo CLI, an OpenCode fork with the same plugin API). Run every command from the root. `npm run check` includes static checks and unit tests for every package; `npm run test:opencode` and `npm run test:kilo` run one host package's tests. Run `npm run test:package` separately for packed-package validation. `npm run build` builds the host packages with tsdown (`tsdown.config.mjs`), which inlines the core into each one's `dist/`: one shared chunk that both the server and TUI entries import, so they share one copy of the core's module state. Every other import stays external; the build fails if any `node_modules` code would be inlined, and `npm run test:package` checks the packed output.

Each host package's `src/host.ts` is the `Host` profile (`packages/core/src/host.ts`) that its `server.ts` and `tui.ts` pass to the core's `createServerPlugin` and `createTuiPlugin`. Keep the host packages that thin: put behaviour in the core, parameterised by the profile, preferring data over host checks; a profile function is fine where data isn't enough, such as Kilo's `providerSetup`. Host-dependent core functions take the host as their first argument. The core imports host packages with `import type` only and has no runtime dependency on them (`packages/core/tests/host-independence.test.ts` enforces this). The core has no peer dependencies: an optional peer pinned to a host range blocks installs next to a newer host. Its runtime dependencies (`jsonc-parser`) are repeated in each host package's `dependencies` with the same caret range, since the bundle imports them. Host differences such as line-break trimming in paths, the catalog source variable and the data-directory state fallback are fields of the profile, so OpenCode keeps OpenCode's behaviour. The host packages never name the core in their manifests: npm links every workspace package into the root `node_modules`, and the core's `exports` point at its TypeScript source, so typechecking, lint, tests and the build all read the source with no core build. The core is typed against OpenCode's types; `packages/kilo/tsconfig.core.json`, part of the Kilo `typecheck`, checks it against Kilo's too. Kilo's types are nominally different from OpenCode's, so the Kilo entries cast the core's plugin to Kilo's types. Package scripts call the root TypeScript (`node ../../node_modules/typescript/bin/tsc`), because a dependency installs an older one in `packages/kilo/node_modules`.

Each host package has a server plugin (the root and `./server` exports) and a TUI plugin (`./tui`), so users add it to `plugin` in both the host's config (`opencode.jsonc` or `kilo.jsonc`) and its `tui.jsonc`. Keep every export path the same in both host packages.

The server `config` hook resolves each agent's `modelRef` and must never throw. It replaces `config.agent` with new objects instead of editing agents in place, because the host keeps the global config's agent objects for the whole process and a stripped `modelRef` would be lost on the next reload. It publishes what it applied in its own `plugin` entry's options (`packages/core/src/report.ts`), which the TUI reads through `/config` for `/model-config` and fallback toasts. The built-in agent names in each host's `src/host.ts` and `schema.json` follow that supported host; Kilo also renames `build` to `code` and gates `scout` behind its experimental variables. Providers load after the `config` hook, so `packages/core/src/fallback.ts` checks refs against connected providers on the first event and in `chat.message`, saves that availability per directory and provider setup (`providerSetupKey`, which never includes credential values, takes provider variable names from the host's cached models.dev catalog when there is one, and on Kilo includes the organization) in the state directory for the next `config` hook, moves a prompt off an unavailable model (toasting it through `client.tui.showToast` once per process, since clients without the TUI plugin never see the report), and reloads the instance once no session is busy and no PTY is open (tried again when a session goes idle or a PTY exits or is removed, at most three refused disposes per instance, never twice for the same availability). Refs carry a host agent's model settings; `chat.params` gives a request that runs on another model than its agent's applied ref the agent's own `temperature` and `top_p`, since those suit only the ref's model.

Each host package's `@opentui/*` and `solid-js` dev dependencies must stay on the versions that host bundles (0.4.5 for OpenCode, 0.5.11 for Kilo), and its plugin and SDK dev dependencies on one exact version in its supported range; `packages/opencode/tests/opencode-baseline.test.mjs` and `packages/kilo/tests/kilo-baseline.test.mjs` enforce this. Update them only together with the supported range in `packages/opencode/tests/opencode.json` or `packages/kilo/tests/kilo.json`. The core's type-only dev dependencies follow OpenCode's.

`scripts/validate-release.mjs` validates the manifests for the Release workflow, which publishes the OpenCode and then the Kilo package in one run; it also requires the core to stay private at the release version and the host packages never to name it.

The GitHub wiki is published from `docs/wiki/`: the Wiki workflow replaces the wiki with that folder on every push to `main` that changes it, so edit pages there, never in the wiki itself. Each file is one page named after its filename, with `_Sidebar.md` as the sidebar; link pages by name, as in `[Usage](Usage)`. One wiki covers both hosts; pages use OpenCode's names, and the Usage page's Host differences section lists Kilo's. Keep in-depth user and developer guides in the wiki. Each package's README is what npm shows for it: a short introduction and install for its host that links to the wiki. Keep the root README minimal.

Write documentation for knowledgeable OpenCode and Kilo users: explain plugin-specific concepts without host or package-install basics or unnecessary cautions. Keep installation examples simple and unversioned. Keep maintainer publishing and release-process walkthroughs out of the README and user pages; the wiki's Developer pages hold them, and release notes are still appropriate.

The plugin's state machines are documented in [docs/state-machines.md](docs/state-machines.md). Update it in the same PR as any change to their states, triggers or exits, with tests for each transition and failure path the change adds or alters.

## Contributor workflows

Request an independent user review for changes to model refs, `models.jsonc` defaults, profiles or built-in agent settings, the profile picker, fallbacks, toasts or user-facing documentation: `opencode-user-review` when the change reaches OpenCode (`packages/core` or `packages/opencode`) and `kilo-user-review` when it reaches Kilo (`packages/core` or `packages/kilo`). Unrelated changes do not need it. Give the reviewer the diff/base and relevant test or runtime evidence.

Use `.agents/skills/native-package-verification/SKILL.md` to select applicable package and host checks; it is not an additional review role. The [agent tooling conventions](https://github.com/lunchbox-labs/.github/blob/main/agent-guidance/agent-tooling.md) cover the file layout, invocation in each tool and reviewer permissions.
